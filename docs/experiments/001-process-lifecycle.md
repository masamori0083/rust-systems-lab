# エージェントと子プロセスの親子関係・待機・終了

実施日：2026年10月28日。本人がUbuntu 24.04.5 LTS / aarch64、Rust 1.96.0で実行し、チャットへ提示した出力に基づく記録。AIが手順の提示と解釈の支援、記録を担当した。ソース変更はない。

## 予測

本人は、`status()`で子プロセスの終了を待つエージェントの状態を `S` と予測した。Bashの `S` は生存中の待機、`sleep 60` は60秒の経過を待つと解釈した。

## 証拠

ターミナル①で、ビルド済みエージェントを実行する。

```bash
./target/debug/linux-job-agent /bin/sleep 60
```

実行中にターミナル②で観測した。

```text
$ ps -C linux-job-agent,sleep -o pid,ppid,state,args
    PID    PPID S COMMAND
   3795    1635 S ./target/debug/linux-job-agent /bin/sleep 60
   3796    3795 S /bin/sleep 60
```

子のPPID 3795がエージェントのPIDと一致する。両方の状態はSだった。別の実行時に得た3766・3767とは別のPIDであり、再現時にも新しいPIDを使う。

親の確認と、同じプロセスの別の情報源による確認も行った。

```text
$ ps -p 1635 -o pid,ppid,args
    PID    PPID COMMAND
   1635    1634 -bash
$ awk '/^(Name|State|Pid|PPid):/' /proc/1635/status
Name: bash
State: S (sleeping)
Pid: 1635
PPid: 1634
```

60秒経過後、ターミナル①にプロンプトが戻った後の確認では、見出しだけが表示された。

```text
$ ps -p 3795,3796 -o pid,ppid,state,args
    PID    PPID S COMMAND
```

## 解釈と判断

- 親子関係の根拠はPIDの大小ではなく、子のPPIDと親のPIDの一致。本人の最初の「PIDが大きいから子」という解釈に対し、AIがこの読み方を説明した。
- エージェントの状態Sは予測と一致した。`status()`で子の終了を待つ動作と整合する。`sleep`もSだったが、待っている対象は時間の経過。状態Sだけから具体的な待ち対象までは断定できない。
- 終了後の観測時点では、指定した2つのPIDの行は表示されなかった。このps観測だけでは途中の状態遷移や実際のシステムコールまでは分からない。続くstraceの観測を下に記す。反復時の資源の増減は観測していない。
- Bashが入力待ちという説明は、プロンプトで待機している状況に基づく解釈。PPID 1634のプログラムは調べていない。
- 待機方式の変更は行わない。CPU使用量は計測しておらず、Sの観測から使用率や性能改善の数値を主張しない。

PIDはその実行の一時的な値。再現時は実行中の出力からPIDを取り直し、プロセス終了後のPID再利用にも注意する。

## 追加観測：終了待ちのシステムコール

本人は、エージェントが終了を繰り返し問い合わせるのではなく、OSに終了待ちを依頼して結果を待つと予測した。本人が実行したコマンド：

```bash
strace -f -e trace=%process ./target/debug/linux-job-agent /bin/sleep 2
```

提示された出力の抜粋（親3811、子3812）：

```text
[pid 3811] wait4(3812, <unfinished ...>
[pid 3812] exit_group(0) = ?
[pid 3812] +++ exited with 0 +++
<... wait4 resumed>[{WIFEXITED(s) && WEXITSTATUS(s) == 0}], 0, NULL) = 3812
```

この実行では、親がwait4を呼び始め、子が終了し、その後にwait4が子のPIDと終了情報を返している。予測と整合する。`unfinished`と`resumed`は同じ呼び出しの表示が分かれたもので、再呼び出しではない。

本人は当初、待ち始める時点と結果が返る時点を混同していた。AIが上記3段階に分けて説明した後、本人は子の終了後にwait4が戻ると説明し直した。支援後の理解として記録する。

同じログではclone3、子のexecve、最後の親のexit_group(0)も観測された。APIの役割とログの読み方の説明後、本人は親3811が子を作り、子3812がsleepを実行すると解釈した。発言中にclone3の3をPIDとする混同があり、AIが3はAPI名の一部と訂正した。execveで実行プログラムが変わってもPIDは3812のままと説明した。この訂正後の本人による独力の再説明はまだ行っていない。

RustのAPI名から常にforkを使うとは決めつけない。今回のフィルタはプロセス関連のみで、sleepの時間待ちの呼び出しや全システムコールは対象外。内部で一時的に生じる状態すべてや、反復時のリーク、CPU使用量は検証していない。
