# TCPで1回だけreadする場合の制約

実施日：2026年10月29日。Mac arm64、Rust 1.96.0。本人が実装・実行し、チャットへ提示した出力に基づく。AIがAPIの短い例、構文説明、実験手順、レビューと記録を担当。AIはソースを編集していない。

## 実装と確認

本人のコードは127.0.0.1:9000で1接続をacceptし、1024バイトの配列に1回readする。受信に成功すると、`&buffer[..n]` を同じTcpStreamのwrite_allへ渡す。終了すると接続も閉じる。

```bash
printf 'hello\n' | nc 127.0.0.1 9000
```

段階的な実装中に本人が提示した結果：

- readの結果：`Ok(6)`。
- 実際に読んだ範囲の表示：`[104, 101, 108, 108, 111, 10]`。本人は最後の10を送信した改行 `\n` と解釈した。
- write_all追加後：送信側にhelloが返り、Rust側に `Ok(())` が表示された。

## 予測と実験

本人は「バッファが1024バイトでreadを1回しか呼ばないため、2000バイトを送っても最大1024バイトしか返せない」と予測した。

Rust側をcargo runで再起動し、別のMacのターミナルで実行した。

```bash
head -c 2000 /dev/zero | nc 127.0.0.1 9000 | wc -c
```

本人の提示した受信バイト数は `1024`。予測と一致した。エラーの報告はなかった。

## 判断と限界

本人は、バッファを大きくする案と、同じ1024バイトのバッファでreadとwrite_allを繰り返す案から後者を選んだ。理由は、バッファ用のメモリを一定に保って繰り返し処理できるため。

一定なのはここで用意したユーザー空間の配列の容量であり、プロセス全体やカーネル側のメモリを計測したわけではない。1回のreadの量は常に1024バイトになるとは限らない。今回の大きい入力では返却バイト数だけを数え、内容の一致・順序までは比較していない。

## 変更後の比較

本人は最初に空のloopをOk(n)の中に置いた。AIがreadとmatch全体を囲む形の短い骨組みを提示し、空ループではwrite_allに到達しないと説明した。また、本人の質問に対してOk(0)の意味とEOFを説明した。その後、本人はreadとwrite_allを繰り返し、Ok(0)でbreakする版を書いた。AIが保存されたソースを読み確認した。

同じ2000バイトのコマンドを本人が再実行し、返却バイト数 `2000` と、Rust側の `Ok(())` 2行を提示した。今回の条件では、1回だけ読む版の1024バイトから、ループ版の2000バイトへ改善した。write_allが2回成功したと分かるが、各readのサイズは出力していないため1024と976だったとは断定しない。内容・順序の比較と、EOFを受けた時点のログは未提示。

AIの指摘を受け、本人はreadとwrite_allのErrで理由を表示してbreakする処理を追加した。AIが保存されたソースで分岐を確認した。本人は修正後も同じコマンドで返却バイト数2000を提示した。エラー注入による異常系の実行確認は未実施。現状はMac上の1接続のエコー練習であり、上流への転送とLinux上のプロキシ動作は未検証。
