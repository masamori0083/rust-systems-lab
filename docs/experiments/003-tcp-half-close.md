# TCPプロキシでEOFを伝え、応答を受け取る

実施日：2026年11月3日。本人が提示したLinux上の実行結果に基づく記録。

## 目的と予測

クライアントの送信終了を転送先へ伝え、その後の応答をクライアントへ返せるか確認する。

本人は「breakはループを抜けるだけなので、転送先には送信終了が伝わらない」と説明した。AIは、try_cloneしたハンドルが残る構成では、元のハンドルが破棄されるだけでも接続全体が閉じないと説明し、Shutdown::Writeによる片方向の終了を案内した。

本人は、送信終了を通知しない場合でもデータは転送できるが接続が残ると予測した。AIは、今回の転送先がEOFを待って応答する条件では、転送先のEOF待ちとクライアントの応答待ちが解消されない可能性を補足した。この「通知なし」の条件はまだ実行していない。

## 実装と役割

```text
テストクライアント <-> プロキシ :9000 <-> EOF待ちの転送先 :8001
```

- プロキシは本人がRustで実装。追加スレッドでクライアントから転送先へ、メインスレッドで転送先からクライアントへ中継する。AIが構文・API・所有権・EOF処理を説明してレビューした。
- 方向ごとに1024バイトの配列を再利用し、readしたnバイトをwrite_allする。EOF時には書き込み先のShutdown::Writeを呼び、メイン側のループ後にjoinする。
- 転送先の `tcp-proxy/examples/eof_backend.rs` は、本人がbind・acceptの部分を書き、その後の明示的な依頼を受けてAIが読み取りループ・EOF後の固定応答・コメントを追加した。受信内容は保存せず、EOFまで読んでから `EOF received\n` を返す。接続は1件で終了する。
- クライアントはAIが提示した短いPythonコードを本人が実行した。helloと改行を送った後、shutdown(SHUT_WR)で送信だけ閉じ、応答をEOFまで読む。

## 環境と再現手順

本人の実行環境はUbuntu 24.04.5 LTS / aarch64、Rust/Cargo 1.96.0。全プロセスを同じLinuxホストで動かした。負荷は1接続、要求6バイト、固定応答のみ。反復測定や性能比較は行っていない。

公開用の再現手順では、リポジトリのtcp-proxyディレクトリから別々のターミナルで次を起動する。

```bash
# 転送先サーバー
cargo run --example eof_backend -j1
```

```bash
# プロキシ
cargo run --bin tcp-proxy -j1
```

待受後、[READMEのクライアント](../../tcp-proxy/README.md#send-a-request)を同じホストの別ターミナルで実行する。通常のcurlはHTTP要求後に送信側を閉じないため、今回のEOF待ちサーバーのクライアントには使わない。両Rustプログラムは1接続ごとに再起動が必要。

本人の実際の実行時は、AIが転送先だけをバックグラウンド起動し、本人がプロキシとクライアントを別のターミナルで動かした。上記はログを見やすくするため、同じサーバーを手前のターミナルで動かす手順として整理したもの。

## 本人が提示した証拠

クライアントの応答：

```text
応答: b'EOF received\n'
```

転送先のログから、接続相手の一時ポートを省いた抜粋：

```text
待ち受け中: 127.0.0.1:8001
受信: 6 バイト
EOFを受信しました
応答を書き込みました
```

プロキシの出力は転送先127.0.0.1:8001への接続を示し、その後プロンプトへ戻った。クライアントも受信ループを抜けた。

この条件では、クライアントの送信終了が転送先まで伝わり、転送先が応答を返し、クライアントが応答とEOFを受け取ったことを確認できた。プロキシのjoinを含む正常系も終了した。

先行するHTTPの確認では、転送先を8000番のHTTPサーバーにした版で、本人がHTTP/1.0 200 OK、本文、curlの終了コード0、プロキシのプロンプト復帰を提示した。現在のコードはEOF待ち実験用の8001番へ変更されている。

## 判断と限界

- 方向別のスレッドとEOF時の片方向終了により、この要求・応答の正常系を動かせた。相手がEOFを必要とする場合は、単にループを抜けることと送信終了の通知を区別する。
- 応答は固定文字列と一致したが、転送先は要求内容を比較していない。ログの6バイトという量だけでは、要求の任意の内容・順序の完全性までは示せない。
- shutdownを外した条件の比較は未実施であり、予測した待ち続ける現象を実証したとは扱わない。
- 読み書きエラー時の両方向の停止、タイムアウト、リセット、負荷、資源使用量は未検証。現在は一方の処理が終わっても、もう一方がreadやwrite、joinで待ち続ける場合がある。
- AIは別途macOS arm64 / Rust 1.96.0で転送先単体を確認し、0・6・2000バイトの入力について、送信終了後の固定応答とサーバー終了を観測した。これは本人のLinux上の中継実験と区別する。
- 今回のGitHub保存前には、AIがmacOS上で現在の転送先・プロキシを起動し、更新したREADMEに掲載したクライアントをそのまま実行した。6バイトの要求で固定応答と受信EOFが得られ、両Rustプログラムの終了コード0を確認した。整形チェック・両パッケージの全ターゲットビルド・cargo testも成功したが、単体テストは各0件。プロキシに既存の未使用項目の警告が2件残る。常設の自動テストを追加したわけではない。
